# 质量检查

目标：确保核心体验被完整传达。

## 方法

- **模拟与试玩分开**：AI 从不同玩家目标回看文本，标明这是模拟审读；手感、可访问性、合作体验需实际原型与真人试玩，不能声称模型读稿已验证。
- **一致性检查**：角色行为、世界规则、时间线。
- **逻辑验证**：因果关系、动机合理性。
- **情感验证**：情感旅程是否完整、高潮是否有铺垫。
- **互动有效性**：动作、选择、探索、表达或协作是否兑现体验承诺，反馈是否清晰；不要求每次互动改变结局。
- **分支完整性**：所有分支是否可达、有没有死路。
- **变量正确性**：状态变量是否正确更新。

## 检查清单（按重要性）

1. **核心体验是否完整传达**（最重要）
2. 角色一致性
3. 世界规则一致性
4. 时间线一致性
5. 逻辑连贯性
6. 情感完整性
7. 互动有效性
8. 分支完整性
9. 变量正确性
10. 设计中的终点可达性（单结局同样适用）

## 互动剧专项检查

在上面的清单之外，逐条核对：

- **路线承接**：角色有没有使用本路线尚未展示或获知的线索？合流场景有没有用到只在某一条分支里建立的事实？
- **状态一致**：对白、效果说明和状态标签是否使用同一字段、方向和数值？有没有另造一套加减分？
- **跨集推进**：已确认的发现或身份，有没有在后续集里被当作新发现重复？
- **时间与结果**：依赖某结果的不可逆行动，是否发生在结果建立之后？「打算」有没有被当成「完成」？
- **终局兑现**：每条通向某结局的路线，是否都在正文里演出了关键行动或结果，而不是只复述目标或以悬念代替？
- **表达与文风**：重复套话是否削弱人物与情境；按作品文风判断，不因出现某个词或句式就判错。
- **格式**：用 `validate_script_format` 校验场景编号、互动标记、选项跳转和分支收束。
- **逻辑预警**：时间线冲突（事件先后与时间标注矛盾）、角色能力矛盾（前面做不到的事后面轻松做到，或反之）、伏笔未规划（埋下后没有回收，或回收的东西没有埋过）。发现时标为提醒，写明涉及的场景编号。

## 局部检查：用工具定位问题

整体质检、复检和质检报告目前暂停，不自动运行，也没有 `script-qa` 工作流可调用。用户明确要求检查某一场、某一集或某条路线时，按下面的方式做：

- `validate_script_format` 校验场景编号、互动标记、选项跳转和分支收束；`analyze_script_graph` 检查场景图（孤立场景、死路、虚假自由、路径膨胀）和状态标注，有《互动设计文档》的变量清单时把它作为 `variables` 传入。
- 想让用户直观看到分支结构时，用 `show_branch_graph`，图由界面绘制，你只需说明结构特点。
- 工具返回的结果如实说明，哪些是错误、哪些是提醒；再用上面的清单逐项审读工具覆盖不到的部分，不声称工具验证了文笔或体验。
- 有项目台账时，先用 `story_ledger_read` 读取，核对伏笔回收与已死亡角色是否再次出场。
- 用户确认修改后再更新剧本；是否保存为报告文件由用户决定。

## 互动设计的三个陷阱

- **承诺落空**：宣称行动影响世界，却没有任何对应反馈。共享目标场景、局部表达或单结局本身不是错误；检查具体承诺、人物回应和理解差异，再决定是否需要改分支。
- **成本失控**：依据唯一场景、状态变体、资产与测试组合评估，不因选项超过 3 个就判错。可通过合流、复用、枢纽或状态条件控制规模，也可按用户预算保留复杂结构。
- **状态遗忘**：承诺持续影响却从未读取，或未走路线的状态进入当前路线。局部表达不需要长线标志；按实际用途删除多余状态或补足后续反馈，不设置影响比例门槛。

## 体验平衡与遗忘元素

- 对比不同路径在长度、内容深度、难度和奖励上的差距，差距过大的要补偿或削减。
- 角色、伏笔和支线如果连续很多集没有出现，要提醒用户是否遗忘，或安排回收。
- 需要展开时，用知识库检索「互动体验平衡」「有意义的选择」「玩家心理」。

## 检查分级

按用户的阶段选一档，默认标准档，并告诉用户这次用的是哪一档：

| 档位 | 检查什么                                                                                                 | 什么时候用               |
| ---- | -------------------------------------------------------------------------------------------------------- | ------------------------ |
| 快速 | 格式、场景图与状态标注：`validate_script_format`、`analyze_script_graph`（有变量清单时传入 `variables`） | 写完一场或一集，边写边查 |
| 标准 | 快速档，加状态与逻辑（变量先定义后使用、无互斥状态同时为真、无孤儿标志）、体验量化（见下）、三个陷阱     | 一整集或一条路线写完     |
| 深度 | 标准档，加台账对照、对照创作原则逐条核对                                                                 | 整部完成、交付之前       |

**体验量化与工具边界**：

- 路径长度、字数、动作频率是定位问题的线索，不是统一合格线；捷径、留白、日常和隐藏路线可以有意不等长，检查实际体验与承诺。
- 选项按可读性与当前工具 schema 校验；选择组件的数量限制不推广为动作、搜索、观察等全部交互的定义。
- 动作型互动另查输入反馈、误触、取消、超时与恢复；没有可运行原型的项目标记待验证。
- 现有图分析工具会产生选项数、相似路径等启发式提示；如实展示返回结果，并结合目标解释是否需调整，不把提示升级为普遍创作禁令。格式硬错误仍须修复。工具未覆盖的动作与复杂状态规则不能宣称已验证。

**对照创作原则**：项目的《需求确认》里写了创作原则时，深度档要逐条核对：每条原则列出「通过」或「违反」，违反的指出场景编号和原文。没有写明创作原则的项目，不凭空编造原则。

## 工作步骤

1. 先确认检查范围（整部、某几集或某条分支），并读取对应的产出物。
2. 按清单逐项检查，每个问题写明：位置（场景编号）、问题、依据、严重程度。
3. 无法确认的内容标为「需人工确认」，不要凭印象判断。
4. 给每个问题一个具体的修复建议。

## 产出：《质量检查报告》

- 检查结果汇总（按清单逐项给出通过、有问题或待确认）
- 问题列表
- 修复建议

## 按当前任务选择检查深度

局部修改先用 validate_script_format/analyze_script_graph 检查受影响的格式、跳转和状态；整集交付前，再按上面的清单审读，并核对当前需求文档里已确认的创作原则、互动设计里的变量和项目台账。发布前复查跨集承接、结局兑现和关键路径；不声称工具完成了未实现的所有状态组合穷举。

用户没有提供原则或变量时保持明确的未提供状态。审读前先读当前项目的需求确认和互动设计文件，不从旧对话猜测。质检结论以工具实际返回为准，不能承诺检查用时。
