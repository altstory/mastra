# 状态变量设计规范

此处前缀与范围用于当前状态剧本的表达约定，不是所有叙事机制的完整数据模型。设计新型动作时先说明事件与含义，再核查工具实际支持。

## 变量类型

| 类型 | 前缀     | 取值     | 用途               | 例子                   |
| ---- | -------- | -------- | ------------------ | ---------------------- |
| 数值 | SV_      | 0 到 100 | 渐进变化的程度     | SV_affection、SV_trust |
| 标志 | FLAG_    | 是或否   | 一次性事件是否发生 | FLAG_met_heroine       |
| 计数 | COUNTER_ | 累计     | 统计某类行为的次数 | COUNTER_lies           |

变化的写法：`SV_name += 10`、`SV_name -= 5`、`FLAG_name = true`。

## 可见性

- **可见**：在界面上展示，如好感 80。
- **隐藏**：只在后台记录，如角色不知道的秘密。
- **揭示**：起初隐藏，满足条件后展示。

## 设计要点

- 命名要清楚：`FLAG_found_key`，不要用 `FLAG_event1`、`var1` 这类含糊的名字。
- 每个变量都要有明确的用途，不创建没有用处的变量。
- 重要的状态变化要让玩家看到反馈。
- 定期检查「设而未用」的标志：被设置却从没被读取的变量，应确认它是遗漏、冗余记录，还是只有即时反馈的局部动作；不要求每次行动产生长线变量。
- 设置变量之前，先规划它的生命周期：何时设、何时读、何时失效。

## 与剧本的衔接

- 每个已发生的动作、选择或事件对应的必要状态变化，要写进互动设计文档的状态变量清单。
- 剧本里的对白、效果说明和状态标签，必须使用同一变量、同一方向和同一数值。

## 事件与认知

区分世界当前状态、已发生事件、玩家已知与各角色相信的事。关门不会抹掉曾开过门的历史，听见传闻不等于事实被证明。状态更新需追溯到真实发生的事件，不把未执行的计划或未走路线当事实。时间、物品与信念系统先作为设计说明；不能擅自生成运行器不支持的字段。参考「世界事实、行动历史与角色认知」。
